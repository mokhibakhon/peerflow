What should peerflow.dev/privacy do?

URLs here carry .html, so the extensionless form of every page is a 404 — /privacy, /login, /terms, all of them. The 404 page names the page you meant and offers the link, which is a rescue, not a fix. Four ways to make the address itself work, and they are not equally cheap.

Today's column is measured, against dev/serve.js. The other three are read off Vercel's documented behaviour: I cannot reach vercel.com from this container to try them, and I would rather say so than let four columns look equally verified.

A · Leave it

was · measured

Everyone who types a bare path lands on the 404, reads the suggestion and clicks once more. For: costs nothing and risks nothing; the resolver already turns the common cases into one click. Against: the address a person typed is still wrong, and a shared link like peerflow.dev/privacy looks broken to whoever receives it.

B · cleanUrls: true

a sweep, not a flag

One line in vercel.json, and it does two things — serves /privacy, and permanently redirects /privacy.html to it. That second half is the whole story. Every canonical on this site currently names the .html form, so the moment this ships, all 12 of them point at a URL that redirects, the sitemap advertises 11 more, and all 217 internal links spend a hop. dev/seo-tests.js already fails a page for linking to the redirecting /index.html — this would make that true of everything. For: the cleanest end state of the four, one URL per page and no duplicates. Against: it is not a config change, it is a coordinated rewrite of the site's entire URL surface, and half-done it is worse than not started.

C · Rewrite /privacy to privacy.html

not recommended

About fifteen rewrites entries. Both forms then answer 200 and nothing else changes. For: purely additive — no canonical, link or sitemap entry moves. Against: it leaves two live URLs serving identical content, permanently. The canonical tag does tell Google which one counts, so this is survivable rather than harmful — but it buys exactly what D buys while doubling the URL surface, and anyone who shares /privacy passes their signal through a canonical hop instead of a redirect. There is no case where this beats D.

D · Redirect /privacy to /privacy.html

shipped

The same fifteen entries, as redirects instead of rewrites, pointing the other way. For: it fixes the thing that is actually wrong — a typed address failing — and touches nothing else. Zero canonicals move, zero internal links, zero sitemap entries, and no page gains a second URL. The redirect hop is paid by somebody who typed the form the site does not use, which is what redirects are for. Against: it settles .html as this site's URL shape for good, which is the less fashionable choice; if you ever want the bare form to be canonical, that is option B and this does not move you toward it.

The list has to be written out, not patterned. A blanket /(.*) to /$1.html would catch /assets/…, /robots.txt, /sitemap.xml, the IndexNow key file and /draft, and would loop on anything already ending in .html. Fifteen explicit entries, with a check in dev/seo-tests.js asserting the list covers every page — the same shape as the check that keeps the 404 page's suggestions honest.

What it does not do: /frontend stays a 404. That is a short alias for frontend-study-partner.html, not an extensionless form of it, and it is a separate decision. The 404 page already offers it in one click.
